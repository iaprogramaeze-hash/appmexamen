BACKEND EPET36 — ANÁLISIS Y DISEÑO (v2 corregido)
================================================================================
Aplicaciones que consume este backend:
  1. Landing Page promocional  -> usa únicamente la tabla pr_preinscripcion
  2. SIGME        (Web App)    -> gestión de mesas de exámenes
  3. SIGME-M      (Mobile)     -> inscripción de alumnos a mesas de exámenes

Documento corregido sobre la v1. Los cambios se marcan con [CORREGIDO] y las
decisiones pendientes con [PENDIENTE].

--------------------------------------------------------------------------------
0. STACK TECNOLÓGICO
--------------------------------------------------------------------------------
  - Framework       : FastAPI
  - Base de datos   : PostgreSQL (Neon Tech)
  - ORM             : SQLAlchemy 2.0 (estilo declarativo moderno)
  - Validación      : Pydantic v2
  - Migraciones     : Alembic
  - Autenticación   : JWT (access + refresh con rotación)

  [CORREGIDO — PD-06, CERRADO 2026-10-06] Restricciones operativas derivadas
  de Neon sobre Vercel (serverless):
  - Despliegue en Vercel con FastAPI (soporte zero-config). No hay proceso
    persistente, así que se RETIRA el pool TCP de SQLAlchemy (desaparecen
    pool_pre_ping y pool_recycle) y la aplicación habla con Neon por el
    driver HTTP serverless.
  - Las migraciones de Alembic se ejecutan desde CI/local sobre la conexión
    DIRECTA (host sin sufijo "-pooler"). PgBouncer en modo transaction no
    soporta SET / DDL transaccional confiable.
  - Variables de entorno: nunca en el repo; se definen en el panel de Vercel,
    por entorno. El backend es un servicio INDEPENDIENTE: landing, SIGME y
    SIGME-M viven en sus propios servidores y sólo consumen el API, por lo
    que el CORS es obligatorio (NFR-023 espera el origen exacto de la
    landing).

1. CONVENCIONES DE MODELO DE DATOS  [CORREGIDO — era inconsistente]
--------------------------------------------------------------------------------
  1.1 Prefijos de tabla (obligatorio, según el área):
        pe_  -> personas / datos de contacto
        us_  -> usuarios, seguridad y sesiones
        es_  -> escolar / académico (orientaciones, cursos, mesas)
        pr_  -> preinscripción (landing page)

  1.2 Nombres:
        - Tablas  : snake_case, SINGULAR, prefijo incluido.
                    Ej: pe_persona, es_mesa_examen.  [CORREGIDO: era mix]
        - Columnas: snake_case. NUNCA camelCase.
                    [CORREGIDO] Postgres dobla identificadores a minúsculas y
                    SQLAlchemy los emite entre comillas: camelCase deja comillas
                    forzadas en cada query para siempre.
                    documentoTipoId        -> documento_tipo_id
                    createdAt              -> created_at
                    fechaInicioInscripcion -> fecha_inicio_inscripcion
        - FK      : {tabla}_id     -> persona_id, mesa_examen_id
        - Índices : idx_{tabla}_{columnas}
        - Únicos  : uq_{tabla}_{columnas}
        - Checks  : ck_{tabla}_{regla}

  1.3 Clave primaria: uuid DEFAULT gen_random_uuid()

  1.4 Auditoría estándar en TODA tabla:
        created_at  timestamptz NOT NULL DEFAULT now()
        updated_at  timestamptz          -- [CORREGIDO] ver 1.6
        deleted_at  timestamptz NULL     -- soft delete
      [CORREGIDO] "timestamp" -> timestamptz. Un timestamp sin zona es ambiguo
      con horarios de verano y con clientes en distinta zona.

  1.5 Índice parcial obligatorio en toda tabla con soft delete:
        CREATE INDEX idx_{tabla}_activa ON {tabla}(id) WHERE deleted_at IS NULL;

  1.6 updated_at  [CORREGIDO — era un bug]
      "updated_at timestamptz DEFAULT now()" NO funciona: DEFAULT sólo se
      evalúa en el INSERT y la columna queda congelada para siempre.
      Se resuelve con trigger en base de datos (vale para cualquier cliente):
        CREATE FUNCTION trg_set_updated_at() RETURNS trigger AS $$
        BEGIN NEW.updated_at = now(); RETURN NEW; END; $$ LANGUAGE plpgsql;

        CREATE TRIGGER set_updated_at BEFORE UPDATE ON {tabla}
        FOR EACH ROW EXECUTE FUNCTION trg_set_updated_at();

  1.7 Soft delete + UNIQUE  [CORREGIDO]
      Un unique común impide re-insertar un registro borrado (mismo DNI, mismo
      username). Usar índice único PARCIAL:
        CREATE UNIQUE INDEX uq_persona_documento
          ON pe_persona(documento_tipo_id, documento) WHERE deleted_at IS NULL;

  1.8 ON DELETE se define EXPLÍCITAMENTE en cada FK:
        CASCADE    -> filas dependientes de detalle (junctions)
        RESTRICT   -> referencias que no se pueden perder (persona, materia)
        SET NULL   -> referencias opcionales
      [CORREGIDO] la v1 no definía ninguno: el default es NO ACTION y produce
      errores 23503 en producción.

  1.9 Tablas junction (muchos a muchos):
      [CORREGIDO] PK COMUESTA sobre las dos FK. Sin id surrogate, sin
      created_at/updated_at/deleted_at (el soft delete no tiene sentido en una
      asignación: o existe o no). Sin el par único, un usuario podía tener el
      mismo rol repetido N veces.

  1.10 Texto: usar varchar(n) con límite de negocio donde exista
       (varchar(100) apellido), no text sin límite en todo.

  1.11 Booleanos: nombre tipo activo / predeterminado / consentimiento.
       [CORREGIDO] No prefijo is_ para no desviarse del español del proyecto.

2. SEGURIDAD Y AUTENTICACIÓN  [CORREGIDO — planteo invertido]
--------------------------------------------------------------------------------
  [CORREGIDO] La v1 pedía "la autenticación lo más compleja posible". Eso es un
  ANTIOBJETIVO: la complejidad no aporta seguridad, agrega superficie de ataque
  y errores de implementación. El objetivo correcto es:
      "superficie mínima + defensa en profundidad + estándar conocido".

  2.1 Access Token
      - TTL corto: 15 minutos (máx. 30).
      - Asimétrico: RS256 o ES256 con kid, para rotación de claves.
      - Claims obligatorios: iss, aud, exp, nbf, iat, jti, sid, ver, sub.
      - En el payload: roles, permisos y módulos (para autorizar sin consulta).
      - Nunca datos sensibles en el payload (JWT es sólo firmado, no cifrado).
      - Almacenamiento cliente: memoria (web) / Keychain-Keystore (móvil).
        [CORREGIDO] prohibido localStorage y AsyncStorage.

  2.2 Refresh Token
      - Opaco aleatorio (32 bytes), TTL 7 días.
      - ROTACIÓN: cada uso emite un refresh nuevo y revoca el anterior.
      - REUSE DETECTION: si llega un refresh ya usado -> se revoca toda la
        familia de tokens y se exige login nuevo.
      - En base de datos se guarda SOLO el hash SHA-256.  [CORREGIDO]
        La v1 guardaba token y refreshToken en texto plano: un volcado de la
        base equivalía al robo de todas las sesiones.

  2.3 Tabla de sesiones (us_sesion)
      [CORREGIDO] La v1 dudaba si esta tabla correspondía ("¿no es usuario?").
      SÍ corresponde: es la que habilita rotación, reuse detection y
      "cerrar sesión en todos los dispositivos". Lo que estaba mal era su
      contenido, no su existencia.

  2.4 Endpoints de auth
      - POST /auth/login      -> access + refresh
      - POST /auth/refresh    -> rota el par
      - POST /auth/logout     -> revoca la sesión
      - POST /auth/logout-all -> revoca todas las sesiones del usuario
      - POST /auth/cambiar-clave
      Rate limit: max 5 intentos fallidos por usuario/IP cada 15 minutos;
      tras ello bloqueo temporal (us_usuario.bloqueado_hasta).

  2.5 Contraseñas  [CORREGIDO]
      Algoritmo: Argon2id, m=19456 (19 MiB), t=2, p=1  (OWASP Password Storage).
      bcrypt queda sólo como fallback legacy, con cost >= 10 y tope de 72 bytes.
      Longitud mínima 12 caracteres. Nunca SHA-256 / MD5 puros.

  2.6 Invalidación global  [CORREGIDO — faltaba]
      us_usuario.token_version (claim "ver"). Al cambiar la clave, cambiar un
      rol o bloquear la cuenta: subir token_version. Todo request valida
      ver == token_version vigente, así los access tokens ya emitidos mueren
      aunque tengan TTL pendiente.

  2.7 RBAC
      usuario -> rol -> permiso, más asignación usuario -> módulo.
      Los permisos son granulares y con código, no descripción libre:
        mesa.listar, mesa.crear, mesa.modificar, mesa.eliminar,
        inscripcion.listar, inscripcion.crear, inscripcion.anular,
        persona.listar, persona.modificar, usuario.gestionar,
        reporte.exportar, preinscripcion.crear, preinscripcion.listar.
      Cada endpoint declara su permiso requerido vía dependencia de FastAPI.

  2.8 Alcance por aplicación
      us_modulo contiene: 'landing', 'sigme_web', 'sigme_mobile'.
      El usuario sólo puede operar en los módulos que tiene asignados.
      [CORREGIDO] El prefijo de módulo no reemplaza el permiso: módulo = a qué
      app puede entrar; permiso = qué puede hacer adentro.

  2.9 Landing page (pública, SIN JWT)
      - POST /landing/preinscripcion con rate limit estricto (anti-bots).
      - Validación estricta de payload y tamaño máximo de body.
      - CORS restringido EXCLUSIVAMENTE al origen de la landing.
        [CORREGIDO] Nunca allow_origins=["*"] en producción.
      - Checkbox de consentimiento de datos personales OBLIGATORIO
        (Ley 25.326 — Habeas Data). Guardar fecha de otorgamiento e IP.
      - Sin endpoint de lectura público: la landing sólo ESCRIBE.

3.18 es_mesa_examen           [CORREGIDO — snapshot con política explícita]
--------------------------------------------------------------------------------
CREATE TABLE es_mesa_examen (
    id                uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    convocatoria_id   uuid NOT NULL REFERENCES es_convocatoria(id)
                                     ON DELETE RESTRICT,
    condicion_id      uuid NOT NULL REFERENCES es_condicion(id)
                                     ON DELETE RESTRICT,
    materia_id        uuid NOT NULL REFERENCES es_materia(id)
                                     ON DELETE RESTRICT,
    grupo_id          uuid NOT NULL REFERENCES es_grupo_horario(id)
                                     ON DELETE RESTRICT,   -- ver §3.22
    fecha             date NOT NULL,
    hora              time,
    -- RB-29: fecha y hora son una COPIA SINCRONIZADA del grupo (§3.22): se
    -- actualizan en la MISMA transacción en que se edita el grupo. No son
    -- atributos libres de la mesa.
    estado            varchar(20) NOT NULL DEFAULT 'planificada'
                      CHECK (estado IN ('planificada','cerrada','realizada')),

    -- SNAPSHOT (copia inmutable de la asignación)
    -- Política RB-11: se recalcula SOLO al editar la asignación de la mesa
    -- (cambiar materia/condición). NUNCA cuando se renombra la tabla origen.
    orientacion_nombre varchar(150) NOT NULL,
    curso_nombre       varchar(100) NOT NULL,
    materia_nombre     varchar(150) NOT NULL,
    condicion_nombre   varchar(50)  NOT NULL,

    created_at        timestamptz NOT NULL DEFAULT now(),
    updated_at        timestamptz,
    deleted_at        timestamptz

CREATE UNIQUE INDEX uq_mesa_unica
    ON es_mesa_examen(convocatoria_id, materia_id, condicion_id, fecha)
    WHERE deleted_at IS NULL;
-- PD-13 [CERRADO — 2026-10-06]: se AGREGA convocatoria_id — el índice anterior

CREATE VIEW vw_mesa_con_alumnos AS
SELECT m.*
FROM es_mesa_examen m
WHERE m.deleted_at IS NULL
  AND EXISTS (
      SELECT 1 FROM es_mesa_inscripcion i
      WHERE i.mesa_examen_id = m.id
        AND i.estado = 'inscripto'

COMMENT ON COLUMN es_mesa_examen.materia_nombre IS

-- acta/reporte debe reflejar el nombre vigente cuando se creó la mesa, no el

-- Type 1: hace falta que la política de actualización esté escrita, y lo está
-- en RB-11.
--
-- Razón: las mesas vencidas dejan de listarse en SIGME, por lo que un renombre
-- futuro de una orientación/curso/materia no debe reescribir mesas históricas
-- ya rendidas.
--
-- NO existe vista v_mesa_examen: el snapshot es la única vía de lectura para

-- Si al editar una mesa se cambia materia_id/condicion_id, el service debe
-- RECALCULAR el snapshot correspondiente en la misma transacción.

3.19 es_mesa_inscripcion      [CORREGIDO — unicidad y trazabilidad]
--------------------------------------------------------------------------------
CREATE TABLE es_mesa_inscripcion (
    id               uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    usuario_id       uuid NOT NULL REFERENCES us_usuario(id)
                                  ON DELETE RESTRICT,   -- alumno que se inscribe
    mesa_examen_id   uuid NOT NULL REFERENCES es_mesa_examen(id)
                                  ON DELETE RESTRICT,
    convocatoria_id  uuid NOT NULL REFERENCES es_convocatoria(id)
                                  ON DELETE RESTRICT,
    -- COPIA de seguimiento de la mesa (igual que los snapshot de 3.18):
    -- se fija UNA vez al crear la inscripción desde la mesa y NUNCA cambia.
    -- Existe para poder imponer la unicidad por materia a nivel de base de
    -- datos, que es lo que pidió el usuario (RB-08).
    materia_id       uuid NOT NULL REFERENCES es_materia(id)
                                  ON DELETE RESTRICT,
    condicion_id     uuid NOT NULL REFERENCES es_condicion(id)
                                  ON DELETE RESTRICT,   -- condición al anotarse
    -- 'anulado': el propio alumno o el secretario revoca la inscripción por
    -- error de elección (se anotó a la mesa de 1° en vez de la de 2°).
    -- Se conserva la fila para auditoría; no se borra.
    --
    -- NO hay estados de asistencia ni de resultado. El sistema no guarda
    -- quién se presentó ni la nota de la mesa (RB-18, RB-21). Quien tiene
    -- permiso de examen antes de rendir, está inscripto: punto.
    estado           varchar(20) NOT NULL DEFAULT 'inscripto'
                     CHECK (estado IN ('inscripto','anulado')),
    inscripto_en     timestamptz NOT NULL DEFAULT now(),
    created_at       timestamptz NOT NULL DEFAULT now(),
    updated_at       timestamptz,
    deleted_at       timestamptz
);
-- RB-08: un alumno NO puede inscribirse dos veces a la MISMA MATERIA dentro
-- de la MISMA CONVOCATORIA. Las convocatorias son independientes: cerrada la
-- de julio y abierta la de septiembre, el alumno vuelve a inscribirse a la
-- misma materia y para el sistema es una inscripción nueva.
-- Un registro 'anulado' NO ocupa cupo: por eso el índice la excluye.
CREATE UNIQUE INDEX uq_inscripcion_unica
    ON es_mesa_inscripcion(convocatoria_id, usuario_id, materia_id)
    WHERE deleted_at IS NULL AND estado <> 'anulado';
CREATE INDEX idx_inscripcion_usuario ON es_mesa_inscripcion(usuario_id);
CREATE INDEX idx_inscripcion_mesa    ON es_mesa_inscripcion(mesa_examen_id);
CREATE INDEX idx_inscripcion_conv    ON es_mesa_inscripcion(convocatoria_id);

-- [CORREGIDO] La v1 no tenía UNIQUE: un alumno podía anotarse dos veces en la
-- misma mesa, y no guardaba la convocatoria ni la condición vigente al momento
-- de la inscripción (si mañana cambia la condición, la inscripción vieja miente).
--
-- [CORREGIDO] La unicidad NO es por mesa sino por MATERIA × CONVOCATORIA
-- (decisión del usuario). Un mismo alumno no rinde dos veces la misma materia
-- en una convocatoria, aunque existan mesas distintas (ej. por condición).

--   nombre_alumno, documento, fecha_nacimiento, orientacion, nombre_tutor, email
--
-- O-1 RESUELTA — CONSENTIMIENTO FUERA DEL SISTEMA:
--   La preinscripción online es sólo una manifestación de interés. El

4. REGLAS DE NEGOCIO CONFIRMADAS
--------------------------------------------------------------------------------
  RB-01  No hay cupo por mesa de exámenes.
  RB-02  No hay etapa de aprobación de inscripciones: anotarse es directo.
  RB-03  Límite de materias por condición: valores por defecto en
         es_condicion.limite_materias — Previa 3, Regular 8, Libre sin límite
         (NULL) — sembrados y editables desde SIGME (PD-02 [CERRADO —
         2026-10-06], PATCH /condiciones en §6). Unidad de conteo: POR
         CONVOCATORIA: el tope se reinicia en cada campaña y se cuenta a lo
         largo de todo el proceso de mesas de esa convocatoria, multi-día y
         multi-grupo incluidos. Se controla SOLO al momento de inscribirse
         (o de anular y reinscribir).
         NUNCA se revalida el día de la mesa: ver RB-17.
  RB-04  Los talleres se modelan como materias normales (es_materia.es_taller).
  RB-05  [PREMISA SIN VIGENCIA — RB-27 y PD-14, 2026-10-01] La premisa de
         esta regla ya no se sostiene: con grupos la convocatoria abarca
         varios días de rendición (RB-27) y ya no declara ninguna fecha
         común de exámenes (PD-14), por lo que tampoco queda una excepción
         de la que desviarse. Premisa original, SIN VIGENCIA: "Todas las
         mesas se rinden el mismo día salvo mesa especial".
         [ACTUALIZADO por RB-27 — 2026-10-01] La convocatoria abarca N días
         de rendición: un grupo de mesas por fecha y hora (RB-27). La
         conclusión se MANTIENE: hay UNA sola ventana de inscripción por
         convocatoria, y cierra antes de la primera fecha de grupo.
  RB-06  Un alumno puede anotarse a una o varias mesas dentro de la ventana.
  RB-07  Cerrada la ventana, SIGME-M sólo permite CONSULTAR la fecha de rendir;
         no admite nuevas inscripciones ni anulaciones.
  RB-08  Un alumno NO se inscribe dos veces a la MISMA MATERIA dentro de la
         MISMA CONVOCATORIA (uq_inscripcion_unica por
         convocatoria × alumno × materia). NO es unicidad por mesa.
  RB-08b Se puede ANULAR la propia inscripción por error de elección; se
         conserva la fila como 'anulado' y no ocupa en el índice. Se mantiene
         el resto de las inscripciones. Límite de RB-07: sólo DURANTE la
         ventana de inscripción de la convocatoria.
  RB-08c Al anular, se puede inscribir a la mesa correcta sólo si no se viola
         el máximo de materias que impone la condición (ver RB-03).
  RB-09  Un alumno no puede inscribirse si la convocatoria está inactiva o
         fuera de la ventana de fechas.
  RB-10  La landing sólo ESCRIBE pr_preinscripcion; no expone lectura pública.
  RB-11  SNAPSHOT de es_mesa_examen: se recalcula SOLO cuando un usuario edita
         la asignación de la mesa (cambia materia_id o condicion_id), en la
         misma transacción. NUNCA se recalcula cuando se renombra la tabla
         origen (es_materia, es_curso, es_orientacion, es_condicion): las mesas
         históricas conservan el nombre con que fueron creadas.
  RB-12  No existe vista v_mesa_examen. Los reportes leen directamente las
          columnas snapshot de es_mesa_examen; los FK se usan para filtrar y
          navegar.
  RB-13  PREINSCRIPCIÓN: repetir el formulario NO es error. Es un UPSERT sobre
          (anio_lectivo, documento): si no existe INSERT (201), si existe
          UPDATE de los campos mutables (200). La validación de los datos
          (resumen + doble confirmación) la hace la LANDING.
  RB-14  PREINSCRIPCIÓN: existe UNA sola ventana vigente (pr_ventana, desde/hasta).
          Fuera de ella el POST responde 409 ventana-cerrada. Fuera del
          sistema: el consentimiento se recoge en formulario físico posterior.
  RB-15  SIN DIVISIÓN NI TURNO. Todas las divisiones de un año (1°A, 1°D, 1°G…)
         y todos los turnos comparten exactamente las mismas materias, por lo
         que el modelo NO contempla división de curso ni turno. `es_curso`
         identifica el AÑO (1°, 2°, 3°…), no la letra.
  RB-16  LA CONVOCATORIA DELIMITA TODO. Cerrado el día de rendir, la convocatoria
         se cierra; en la fecha que corresponda se abre OTRA convocatoria para
         todas las materias. Un alumno que no aprobó se vuelve a inscribir con
         los mismos datos y para el sistema es una inscripción y una mesa
         NUEVAS. Por eso `es_convocatoria.fecha_*` es la referencia que evita
         que los datos se repitan entre campañas.
         [ACTUALIZADO por RB-27 — 2026-10-01] "El día de rendir" es la
         ÚLTIMA fecha de los grupos de la convocatoria (RB-27); ya no hay una
         única fecha común de todas las mesas.
  RB-17  LISTA FIJA AL CERRAR LA VENTANA. Cumplida `fecha_fin_inscripcion` nadie
         se inscribe más. Los inscriptos hasta ese momento son los DEFINITIVOS:
         el sistema NO revalida nada el día de rendir.
  RB-18  SIN REVALIDACIÓN NI REGISTRO DE INASISTENCIA. Quien no se presenta a la
         mesa escapa al sistema: no se anota que faltó. Lo que hay en la lista
         al día de rendir es lo que hay.
  RB-21  EL SISTEMA NO GUARDA NOTAS. Ninguno de los sistemas en juego almacena
         el resultado de la mesa por alumno: no hay `nota`, no hay
         aprobado/desaprobado, no hay rectificación. El resultado vive en el
         acta en papel. `es_mesa_inscripcion` sólo sabe QUE el alumno está
         inscripto — ni más ni menos. Por eso `estado` sólo admite
         'inscripto' y 'anulado'.
  RB-19  TRES REPORTES DE CIERRE (salen de SIGME, en papel):
         · PERMISO DE EXAMEN — individual, por alumno: detalla qué materias
           rinde ese día. Se entrega en mano al alumno.
         · ACTA VOLANTE — por mesa de una materia: todos los alumnos
           inscriptos en esa mesa. Se entrega a los profesores evaluadores.
         · PLANILLA DE GRUPOS (RB-32) — por convocatoria: cada grupo con las
           mesas que se rinden en él. [CONFIRMADO — 2026-10-04] incluida en
           la primera entrega (regla original de 2026-10-01, cuando su
           alcance todavía no estaba comprometido).
  RB-20  [REVOCADA por RB-28 — 2026-10-01] LA MESA LA CREA EL PRIMERO EN
         ANOTARSE. NO VIGENTE: su justificación (48 a 60 mesas por
         orientación, imposibles de habilitar una a una) quedó resuelta por
         la alta MASIVA del secretario (RB-28), que crea N mesas de una. El
         ID se conserva para no renumerar. Texto original, SIN VIGENCIA:
         El alumno elige en cascada orientación → curso → materia →
         condición; al aceptar:
           · No existe `es_mesa_examen` para esa combinación en la convocatoria
             -> el BACKEND LA CREA y enlaza la inscripción.
           · Ya existe -> sólo se anexa la inscripción.
         Motivo del usuario: por orientación hay 6 cursos × de 8 a 10 materias
         = 48 a 60 mesas. Es imposible que el secretario las habilite una a una.
         Consecuencia: el alta de mesas NO es tarea de administración.
         El `fecha` de la mesa sale de `es_convocatoria.fecha_mesa` (fecha común)
         y los 4 snapshot se rellenan de la cascada elegida por el alumno.
  RB-22  SÓLO SE ENTREGAN MESAS CON ALUMNOS. Todo listado y toda impresión
         devuelven únicamente las mesas con AL MENOS UNA INSCRIPCIÓN ACTIVA
         (estado = 'inscripto'). Las mesas que quedaron con 0 alumnos —porque
         todos anularon— se IGNORAN, no se borran.
         Así, la impresión masiva de permisos de examen sale "a toda ley",
         agrupando sólo mesas reales.
  RB-23  LÍMITE INCLUSIVO Y POR FECHA DE CALENDARIO. `fecha_fin_inscripcion`
         se respeta hasta las 23:59:59 de ese día inclusive. A las 00:00:00
         del día siguiente ya cambió de fecha y la inscripción está cerrada.
         Implementación: comparar `current_date` (timezone del backend,
         America/Argentina/Buenos_Aires) contra `fecha_fin_inscripcion`;
         NO usar un timestamp crudo de UTC ni sumar horas.
         Vale igual para `fecha_inicio_inscripcion` y para `pr_ventana`.
  RB-24  NOTIFICACIONES — 3 canales, sólo por EVENTOS DE USUARIO (v1):
         · PUSH (SIGME-M)  -> se abrieron / se cerraron las inscripciones.
         · IN-APP (SIGME)  -> "campanita". Multi-rol: cualquiera de los roles
                              (secretario, director, admin, superadmin) puede

  RB-28  EL SECRETARIO CREA LOS GRUPOS Y SUS MESAS (ALTA MASIVA). El alta de

  RB-29  TODA MESA TIENE GRUPO (COPIA SINCRONIZADA). `es_mesa_examen.grupo_id`
